# Riskora AI

Riskora AI is a prototype payment-risk investigation platform for the Razorpay AI Buildathon. Phase 1 establishes a reproducible fraud-modeling foundation; later phases will add FastAPI persistence, bounded agents, RAG, policy controls, human review, and the dashboard.

## Phase 1: Data and ML pipeline

The default dataset is deterministic synthetic transaction data generated by `ml/data/generate_demo.py`. It is suitable for exercising the pipeline and demo workflows, but its labels and metrics are not representative of production performance. Engineered context fields such as device risk, velocity, country change, and impossible travel are explicitly simulated in this dataset.

For a real-data experiment, pass a CSV containing the same documented columns to the trainer. A suitable public starting point is the [Kaggle Credit Card Fraud Detection dataset](https://www.kaggle.com/datasets/mlg-ulb/creditcardfraud); it has serious schema and feature limitations for this product because it does not expose customer behavior, device, location, or merchant context. Those production signals should not be claimed from that dataset without a separate feature source.

The trainer compares calibrated class-weighted Logistic Regression and a class-weighted Random Forest using a stratified 60/20/20 train/validation/test split. The selected model is the measured validation winner by fraud-class F1, with ROC-AUC as a tie-breaker; the untouched test set is evaluated only after selection. Metrics are written to `ml/models/metrics.json` and the serialized artifact to `ml/models/risk_model.joblib`; generated artifacts are ignored by git.

Business metrics use explicit demo assumptions: false-positive cost is 2.0 currency units, while prevented and missed loss use the mean fraud amount in the holdout set. These are reporting assumptions, not financial forecasts.

## Setup

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -e ".[dev]"
python -m ml.data.generate_demo
python -m ml.training.train
pytest
```

Score one transaction after training:

```python
from ml.inference.predict import predict_transaction
result = predict_transaction(transaction, "ml/models/risk_model.joblib")
```

The model returns `fraud_probability`, `risk_score`, `risk_level`, and `model_version`. Risk score is the model probability multiplied by 100. The Phase 2 policy engine applies configurable LOW `<30`, MEDIUM `<60`, HIGH `<85`, and CRITICAL `>=85` thresholds.

## Phase 2: Risk engine

Phase 2 adds three independent deterministic services in `risk_engine/`. `BehaviorEngine` emits structured signals from fields available in the dataset, including amount deviation, velocity, device, location, time, failed attempts, fraud history, and impossible travel. Missing context is marked `unavailable` with a `future-production-signal` source; no unavailable production data is inferred. The strongest available behavioral severity becomes the behavioral score.

`PolicyEngine` uses configurable `PolicyConfig` thresholds and contains no LLM or agent dependency. It maps LOW to APPROVE, MEDIUM to REVIEW, HIGH to HOLD plus HUMAN_REVIEW, and CRITICAL to BLOCK. High-risk combinations and unavailable evidence can add deterministic reason codes. `RiskAssessmentService` preserves the full ML result and behavioral signals, then uses the conservative maximum of ML and behavioral scores before policy evaluation, so severe evidence cannot be diluted.

Synthetic Phase 2 scenarios are defined in `risk_engine/demo_transactions.py`. The normal scenario produces LOW/APPROVE with the trained model. The suspicious scenario contains the requested high-risk signals and may be escalated to CRITICAL/BLOCK when the actual trained model score is critical; this is reported as model behavior rather than overridden to fit a label. The critical scenario produces CRITICAL/BLOCK. These scenarios are for tests and demonstrations only.

## Phase 3: Multi-agent investigation and RAG

Phase 3 adds a bounded LangGraph workflow in `agents/graph/workflow.py`:

`validate -> ML -> Behavior Agent -> Investigation Agent -> Evidence Agent -> Decision Agent -> Policy Engine -> Audit Agent`

The Behavior Agent reuses Phase 2's `BehaviorEngine`. The agents exchange typed `InvestigationState` fields and never invent transaction facts. The Decision Agent creates only a recommendation; it has no payment execution capability. The existing deterministic `PolicyEngine` remains authoritative for permitted actions.

The RAG layer in `rag/` ingests clearly labeled demo/internal Markdown policies into chunks and retrieves evidence with a local TF-IDF vector store. Results preserve source, section, relevance, content, and metadata. Unknown or empty queries return no evidence, and unavailable evidence is surfaced rather than fabricated. This local store is abstract enough to replace with pgvector later.

Run the end-to-end demo after training the model:

```powershell
"E:\Riskora Ai\.venv\Scripts\python.exe" -m ml.training.train
"E:\Riskora Ai\.venv\Scripts\python.exe" scripts\run_investigation.py
```

The demo writes local JSON audit files under `audit/` (ignored by git). Set `LLM_API_KEY` and `LLM_MODEL` in a future LLM-backed summarizer; the current agents are deterministic and work without credentials. Documents in `rag/documents/` are demo/internal guidance and are not official Razorpay policy.

## Phase 4: FastAPI and PostgreSQL

The backend lives under `apps/api/app/` with thin versioned routes, service-layer orchestration, SQLAlchemy repositories/models, JWT role foundations, and Alembic migrations. PostgreSQL is the configured deployment database; the default development URL is SQLite so the local API can be tested without a database server. Set `DATABASE_URL` to the PostgreSQL URL from `.env.example` for the real deployment path.

```powershell
docker compose up -d postgres
alembic upgrade head
python scripts/seed_database.py
uvicorn apps.api.app.main:app --reload
```

The API exposes `/health`, `/health/db`, `/docs`, `/redoc`, transaction endpoints, investigation endpoints, reviewer actions, chronological audit retrieval, and PostgreSQL-backed dashboard queries. Development mode permits a local admin principal for synthetic testing; non-development mode requires a JWT bearer token signed with `JWT_SECRET`. Review actions require a reason and append review, final-action, and audit-recorded events.

## Phase 5: Next.js dashboard

The reviewer dashboard lives under `apps/web/` as a Next.js (App Router) + TypeScript + Tailwind application. It provides a login view backed by the API's JWT/dev-principal auth, a dashboard overview with risk distribution, transaction list with search and status filters, a transaction detail view with the full investigation timeline (ML score, behavioral signals, evidence, decision, policy outcome), reviewer actions with mandatory reason dialogs, chronological audit trail lookup, and a settings page.

```powershell
cd apps\web
npm install
npm run dev
```

The web app expects the FastAPI backend from Phase 4 to be running (default `http://localhost:8000`; configure via `apps/web/.env.local` if different). Development login uses the local admin principal permitted by the API in development mode.

Quality gates: `npm run test` (69 unit tests across API client, auth storage, formatting utilities, and UI components), `npx tsc --noEmit`, and `npm run build` all pass. Pages using `useSearchParams` are wrapped in Suspense boundaries so static prerendering succeeds.

This repository is a test/prototype environment, not a payment processor. Use synthetic or provider test data only. Never store raw card numbers, CVV, or credentials.
